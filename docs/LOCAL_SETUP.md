# Local application Setup evaluation

This builds an **unpublished evaluation installer**, not a release. It contains the recorded normal app, its exact 94-file media runtime, local original notices, a path-bound uninstaller and the original Microsoft prerequisite package. Per-user registration and a Start menu shortcut are implemented; actual supported-Windows registration/lifecycle qualification and updates remain pending. Nothing is installed by the build or inspection scripts.

## Build and inspect

Use the fixed candidate inputs described in [candidate materials](CANDIDATE_MATERIALS.md), [source companion pins](setup-inputs.json), [NSIS inputs](nsis-inputs.json) and [VC prerequisite review](VC_REDIST.md):

```powershell
.\scripts\build-local-setup.ps1 `
  -Executable 'path/to/towavue.exe' `
  -RuntimeDirectory 'path/to/exact-94-file-runtime' `
  -SourceCompanion 'path/to/towavue-sources-195af870-c68cad34.zip' `
  -VcRedist 'path/to/vc_redist.x64.exe' `
  -NsisArchive 'path/to/nsis-3.12.zip' `
  -OutputDirectory 'path/to/fresh-setup-build'

.\scripts\test-local-setup.ps1 `
  -BuildDirectory 'path/to/fresh-setup-build' `
  -SourceCompanion 'path/to/towavue-sources-195af870-c68cad34.zip' `
  -NsisArchive 'path/to/nsis-3.12.zip'

.\scripts\test-setup-prerequisite.ps1
.\scripts\test-setup-registration.ps1
.\scripts\test-setup-fixture.ps1 -NsisArchive 'path/to/nsis-3.12.zip'
```

The builder checks pinned archives, Microsoft package identity/signature and all 95 actual binary bindings before staging. It uses the original portable compiler with `/NOCONFIG /WX`; it does not download, install a toolchain, sign or publish. `BUILD.json` is written only after compilation and final input/staging checks. A directory or executable without that record is incomplete, not a deliverable. Retain failed output for inspection and use a fresh directory for another build.

The current app is 10,301,952 bytes/SHA256 `195af8705605e678a9cbe97aa57a0cdb7cae5e34bf61ee6b60e528b933f93186`. It has not been rebuilt for the installer. The source companion remains 509,515,254 bytes/SHA256 `1fa92321d044ffa380a76caf342a33a4507ca80aca0f620740b75859a02b5d20`. That archive binds app/native sources, not these later installer sources. Installer-source delivery is still a release gate.

## Implemented behavior

- Unicode/zlib, normal-user execution, Welcome, editable destination, progress and Finish. The default is the current user's `Programs/towavue-evaluation` under LocalAppData; a writable empty dedicated local directory can be selected. No automatic application launch or reboot.
- One current-user uninstall entry (`HKCU`, Registry64, `towavue-evaluation`) and one current-user Programs shortcut. Display version remains the workspace's `0.0.0`, explicitly labeled local evaluation. No desktop shortcut, all-users registration, association or automatic update. The uninstall command is quoted and opens the existing confirmation UI.
- Application mode requires native AMD64 and OS build 19045 or later. This check does not qualify an OS or hardware configuration. Silent application installation is refused; silent fixture tests remain supported.
- Shared path checks reject roots, relative/drive-relative paths, UNC/device paths, occupied folders, files in the ancestor chain and reparse points. The app also checks the longest generated payload path against the traditional Windows path limit. Check again after prerequisite interaction, before target writes.
- Generate explicit installation/deletion lists from the verified staging inventory, not recursive extraction/deletion or a second handwritten runtime list. Check every owned directory and payload-bound marker before removing anything. Delete only owned names; remove directories only when empty. Extra user files and media/settings outside the installation are not removed. A locked-file failure retains retry state; no reboot deletion or automatic rollback.
- Run the existing strict Registry64 prerequisite reader through Windows PowerShell's absolute system path, including under 32-bit NSIS. `ExecutionPolicy Bypass` is process-scoped for the bundled reviewed scripts, not a machine setting change. Unknown state stops. Satisfied state skips installation.
- When required, ask before opening the unchanged Microsoft package's full UI with `/install /norestart` and normal UAC elevation. The user controls Microsoft terms acceptance. Wait for that process and recheck registration; only actual exit 0 or 3010 with satisfied registration proceeds. Other codes, including a different-version result, conservatively stop. Preserve 3010 in the Setup exit result and explain manual restart; never restart or launch towavue automatically. Never remove the shared runtime.

The wrapper uses PowerShell `Start-Process -Verb RunAs` to retain the actual child result rather than assuming that a waited shell launch exposes an exit code. Synthetic tests are not evidence of Microsoft's actual UAC, cancellation, HRESULT or reboot behavior. [NSIS execution reference](https://nsis.sourceforge.io/Docs/Chapter4.html#execshellwait).

### Registration ownership and failure order

Registration preflight precedes the VC UI and target writes. Any existing key, even empty, or existing shortcut refuses a fresh installation. After payload and uninstaller creation, write the path-bound marker, then register. A registration failure is not success: retain the folder and use its uninstaller or inspect the failure. This does not promise atomic registry writes or rollback after a permission change/power loss.

Uninstall checks the registration's payload identity and install path before deleting app files. Only after successful payload deletion does it remove registration; locked payload failures therefore retain the uninstall entry for retry. The helper is embedded in both Setup and uninstaller and runs from their private temporary directory, independently of the deleted payload. Remove only known registry values, and delete the key only if empty. Additional values/subkeys remain. A missing registration does not authorize shortcut deletion.

The shortcut's recorded SHA256 authorizes removal only while its bytes remain unchanged. Any byte change, including a possible Shell rewrite, conservatively preserves it and is reported in details. This preservation policy still needs the real first-launch/uninstall lifecycle test. A locked shortcut fails removal before registration values are removed, preserving retry identity. Foreign registration identity stops deletion, not takeover.

`UnicodeShellLink.cs` uses `IShellLinkW` and `IPersistFile` on one synchronous STA with explicit COM release; it never runs or resolves a target. The initial WScript.Shell approach locally rejected Japanese target paths even when an actual executable was copied there; spaces/ampersands/dollars alone worked. Explicit Unicode creation and read-back pass Japanese paths in 32-bit and 64-bit Windows PowerShell. The helper uses the system PowerShell/.NET compiler, not Visual Studio or WSL. [Unicode Shell link interface](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-ishelllinkw), [file persistence](https://learn.microsoft.com/en-us/windows/win32/api/objidl/nn-objidl-ipersistfile).

Registration tests create a fresh `HKCU\Software\towavue\InstallerTests\<GUID>` key and scratch-directory shortcut pointing to harmless fixture files. They verify real Shell link fields, registry types, Unicode, collisions, foreign/missing identity, lock/retry, changed-shortcut and extra-registry-data preservation, missing files and junction refusal. Test GUID keys and generated shortcuts are cleaned up; the real app-list key and Start menu are not written. CI runs this scoped native test in addition to the document-only installer fixture.

The internal registration helper also provides `VerifyUpdate` and `Update` for a same-directory transition. In addition to the target ownership ID/size, the caller must supply the previously recorded `PreviousOwnershipId` and `PreviousSizeKiB`. Verify the existing key/path and String/String/DWord types, accepting only the two supplied identities/sizes, including known partial transitions. Write `EstimatedSize` first and `TowavueOwnershipId` last, then flush. Reversing the previous/target arguments restores the original typed values; repetition is safe. Do not recreate a missing key or infer its ownership, regenerate the shortcut, change the command/path/display fields, or touch unknown values. These two writes are not atomic and do not exclude concurrent registry editing by the same user.

Fixtures cover unchanged verification, forward/reverse repetition, interruptions after each write in both directions, foreign ID/size/path/type/missing previous state and a missing registration. Compare the complete typed value snapshot and shortcut hash; preserve an extra fixture value. These modes are deliberately not exposed by the current NSIS wrapper. Setup must use the bound transaction below instead of coordinating these calls independently; trusted recovery identity persistence, recovery UI and Setup orchestration still need connection before occupied-directory updates can be enabled.

## Verification and open gates

Inspection compares all 95 staged binaries, every selected original against the fixed companion ZIP, all guide links, the generated install/delete lists and build-source hashes. It exercises eight invalid input/output cases, five non-installing Setup probes and the packaged prerequisite's read-only inspection in 32-bit and 64-bit Windows PowerShell. It does not execute the real install section.

Sixteen child-process synthetic cases cover skip/required/unknown, original launch arguments, waiting, success, 3010, failed post-checks, cancellation, busy/different-version/wrapped failure and simulated UAC/reader failure. They use the unchanged wrapper, a private fake reader/launcher and a nonexistent fake package. CI runs these and the harmless shared lifecycle fixture, not the real application installer.

The empty-working-directory probe exposed a shared safety bug: NSIS stores a drive-root assignment as `C:`, and Windows then resolves it against the process working directory. Previous occupied-cwd tests happened to reject the result. Reject roots and drive-relative input **before** resolution; the fixture now tests empty cwd too. No actual root installation or deletion was attempted.

## Read-only update planning

`scripts/get-setup-update-plan.ps1` is the preflight for a future recoverable update, **not an updater**. Existing Setup still refuses occupied directories. The planner does not launch the old uninstaller, change app files, write registry/shortcuts, create a backup or authorize a transaction.

```powershell
.\scripts\get-setup-update-plan.ps1 `
  -InstallDirectory 'path/to/existing-installation' `
  -IncomingPayloadDirectory 'path/to/trusted-build/payload' `
  -IncomingOwnershipId 'towavue-local-<incoming inventory SHA256>'
.\scripts\test-setup-update-plan.ps1
```

It checks the old UTF-16LE marker's path and inventory hash, the caller's expected incoming inventory identity, every recorded file's actual size/hash and exact incoming coverage. The resulting JSON identifies keep/add/replace/remove actions, old metadata bytes for backup, and backup/incoming byte totals. Extra installed user files are left outside the action list; a new file colliding with an unowned path is refused. Altered or missing recorded DLLs stop planning rather than silently restoring the bundled copy. App startup still has no hash allowlist.

Reject duplicate/case-colliding names, traversal/device/stream/wildcard names, reserved installer metadata, file/directory conflicts and reparse points. Expand existing DOS directory aliases before overlap checks and reject short-name aliases in inventory entries. This avoids treating two spellings of one directory as separate trees. [Windows long-path-name API](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-getlongpathnamew).

Read/write exclusive opens of old owned files perform no writes but reject sharing/access failures; handles are immediately released. The result is only a snapshot, not a retained lock or proof that processes cannot start later. An eventual transaction must revalidate, stage backups before replacing anything, avoid hard-link write-through, preserve file/registry/shortcut recovery state, and handle interruption and rollback without discarding user changes. The existing marker does not record the original uninstaller hash: its current bytes are captured for backup only and are never executed or authenticated by this check.

Focused fixtures cover action coverage, user/replacement preservation, repeat/arbitrary cwd, malformed inventories/markers, overlaps/DOS aliases, locks and junctions. A separate full-data fixture compares the actual two 2708-file staged payloads: 2707 keep actions and only the changed inventory replacement. Its marker and uninstaller stand-in are synthetic; this is not installed-app/update or recovery evidence. Original staged payloads remain unchanged.

## File and registration update transaction

`scripts/setup-update-transaction.ps1` is a dot-sourced, **not yet Setup-connected** primitive. `New-TowavueUpdateTransaction` accepts the planner's three inputs plus a caller-supplied new uninstaller, which must be generated/verified by the eventual Setup. It creates independent old/new copies of changed files and the executable in a fresh same-volume sibling directory and writes an immutable journal last, returning `TransactionDirectory` and `JournalSha256`. Unchanged non-app files are still verified/locked, but not copied: they are never mutated or automatically restored over user changes. The future caller must durably retain that digest before calling `Invoke-TowavueUpdateTransaction -Mode Apply`; the digest is a corruption check, not authentication against the same user. Preparation does not change installed files.

The optional `Registration` hashtable contains exactly `RegistrySubKey` and `ShortcutPath`. Preparation uses `setup-update-registration.ps1` to verify the old key against the installed inventory ID, capture its typed previous size, and derive the new ID/size from the incoming file plan. Store the whole transition in the same immutable journal, not a separate caller-edited record. All new journals use schema 3 so earlier readers cannot resume the new two-executable guard protocol; the current reader also accepts previous internal schema-1/2 journals. Missing/foreign registration fails before creating the transaction directory. Both execution directions bind the recorded install path, old/new IDs and new size to the file plan and verify current registry state before file mutations. Omission of `Registration` retains the file-only primitive for existing fixtures; it never infers registration ownership.

Apply repeats the complete planner, verifies every staged/backup file, and acquires sharing-restricted read/write handles to all existing owned targets before mutation. It copies old security/streams into an independent work file and changes only that copy's main data stream. Windows locally refuses ordinary replacement of an open destination even with delete sharing. Therefore the transaction first moves the old name into retained storage, then moves the new work file into place without overwrite or cross-volume fallback. Validate both guard retirement destinations before either move, retire Uninstall.exe first and towavue.exe second before changing payload, even when their bytes are unchanged. Publish the app after payload and registration agree, then publish/restore the uninstaller last. Rollback follows the same ordering. A failure between the first two retirements leaves only the still-consistent old app available; mixed payload has neither installed executable entry point. No process is killed or uninstaller executed by the production helper. [Windows move semantics](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [Windows copy semantics](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfilew).

Rollback may encounter an original executable still at its target: after the first new guard, a legacy app-first interruption, or an interrupted rollback that already restored the app. Validate its old hash and retire that original into the available apply-retired slot, then restore that same object. Do not require a nonexistent backup-retirement name or allocate a replacement copy. Existing occupied/unknown guard destinations are still refusal conditions before either guard move. Forty file-only/joined move boundaries assert guard presence and exact payload/registry states at publication; identical-uninstaller and legacy schema-1/2 first-app-retirement cases also recover. This prevents new launches from the installed paths, not an already running or previously self-copied legacy uninstaller; actual legacy process coordination and product lifecycle remain gates.

Rollback needs the retained directory/digest, not the original incoming tree. Before mutation it checks all current files against the recorded old/new main-stream hashes. Retired files identify the gap between the two moves; a flushed publication receipt distinguishes a later missing published file from an interrupted publication. Unknown content, corrupt recovery data/receipts and sharing failures stop and retain evidence. Restore the validated retired original by renaming it back, not by making another data-file copy: missing/locked originals or missing original parent directories stop before mutation rather than triggering an automatic copy fallback. Rollback itself is restartable at the tested move boundaries and idempotent. A used transaction cannot be applied again; prepare a new one. Restored originals return to the installation; newly rolled-back files, independent backups, receipts and any created empty directories remain recoverable; no recursive cleanup occurs.

For a bound transaction, perform the registration transition after the non-executable files have reached their target state and immediately before publishing the app, in both directions; the uninstaller follows it. A registry write failure during file changes leaves both executables retired. The same journal/digest can then Rollback both files and a known partial registry transition. Unknown registry values stop before files change. A file-unchanged operation can adjust the registry without retiring already consistent executables. Results explicitly distinguish `files_and_registration_applied`/`files_and_registration_rolled_back` from the legacy `payload_applied_registration_pending`/`payload_rolled_back` cases. A partially applied update must be rolled back before preparing a fresh attempt; this is not forward-resume support.

This is not a whole-install atomic transaction. There is a window between publication and its receipt, and the helper does not exclude hostile same-user directory renames/reparse races. It does not verify all alternate streams/security/timestamp changes or promise complete NTFS metadata fidelity. Rollback no longer allocates replacement data copies, but filesystem metadata can still require space; actual full-volume and ACL-denial recovery are not qualified. Full power-loss durability, uninstaller concurrency guards, recovery UI, cleanup and real Windows 10/11 Setup integration remain gates. Existing Setup still rejects occupied directories; these helper results are not an installed-product lifecycle qualification.

`scripts/setup-registered-update.ps1` adds the internal `Invoke-TowavueRegisteredUpdate` entry point. Apply takes the preparation arguments including Registration, prepares the journal, then writes and flushes one REG_SZ `TowavuePendingUpdate` value containing its directory/digest/schema in the existing owned HKCU Registry64 key before changing installed files. Rollback needs only the selected InstallDirectory and Registration, not a caller-retained token or incoming payload. The transaction validates that the journal belongs to that exact selected install/key/shortcut before mutation. A pending record blocks another Apply; malformed, unknown-type or cross-install records are preserved. Clear only the unchanged pointer after successful Apply/Rollback; a crash after complete Apply but before clearing still permits rollback. Recovery files remain retained, not recursively cleaned.

The registered entry point and newly built Setup share a user-SID/registration-key operation lease, so different destinations competing for the same registration also conflict. A common helper derives the global object name. The first creator retains a mutex handle; later creators close their handle and refuse work. Object existence is the lease, without waiting or thread ownership, allowing NSIS section/UI cleanup on different threads. Normal completion/exit closes the handle; termination also releases it once all handles close. The durable pending pointer is independent. The corresponding Windows API lifetime contract is documented in [CreateMutexW](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-createmutexw).

NSIS acquires before registration/prerequisite work and target writes, or before uninstall ownership checks, and holds through all payload/registration/marker changes. Conflict or coordination failure exits with code 4 without application changes; CHECKONLY remains read-only and does not acquire. Abort/GUI exit and silent process teardown release the handle. The new registration helper additionally refuses VerifyRemoval/Remove whenever a pending value exists, including malformed values. This does not retrofit previous binaries. Connecting child coordination, the two-executable file protocol and actual recovery UI remains required before enabling occupied-directory Setup. Do not bypass the child guard or infer update support from a successful new-install lease.

Before launching its Windows PowerShell helpers, NSIS clears only its own inherited PSModulePath so the child host initializes the correct built-in module search. Inheriting PowerShell 7's module path reproduced a missing Get-FileHash in the opposite-bitness Windows PowerShell fixture child; it never reached the concurrency gate. The test launcher now temporarily removes that one process environment variable around child creation and restores the parent value in finally, while retaining child diagnostics. No machine/user environment or execution policy is modified.

Generated child processes terminate after pointer publication/before file changes, between registration writes, and after complete Apply/before pointer deletion. The parent recovers through the selected key without receiving a token from the child and checks exact old file/typed registry/shortcut states. Corrupt or locked journals keep the pointer and allow retry once corrected/released; malformed and cross-install pointers cannot modify either installation. A child of the opposite PowerShell bitness holds the operation mutex while both Apply and Rollback competitors are refused. These tests exercise process termination, not power loss or actual NSIS concurrency.

Native update copy/move calls use extended-length absolute paths after the caller's local-path validation. A private work name reached 263 characters while its installation stayed below the Setup limit; a minimal probe copied under Windows PowerShell but failed under portable PowerShell 7.6.6 until this change. Explicit 263-character copy/source/move and non-overwrite checks cover the bridge without changing host long-path settings. This fixes runtime-host dependence in scratch operations, not the installer's overall path-length policy or complete long-path UX. See the [CopyFileW path contract](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfilew).
