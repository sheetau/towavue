### Registration ownership and failure order

Registration preflight precedes the VC UI and target writes. Any existing key, even empty, or existing shortcut refuses a fresh installation. After payload and uninstaller creation, write the path-bound marker, then register. A registration failure is not success: retain the folder and use its uninstaller or inspect the failure. This does not promise atomic registry writes or rollback after a permission change/power loss.

Uninstall checks the registration's payload identity and install path before deleting app files. Only after successful payload deletion does it remove registration; locked payload failures therefore retain the uninstall entry for retry. The helper is embedded in both Setup and uninstaller and runs from their private temporary directory, independently of the deleted payload. Remove only known registry values, and delete the key only if empty. Additional values/subkeys remain. A missing registration does not authorize shortcut deletion.

The shortcut's recorded SHA256 authorizes removal only while its bytes remain unchanged. Any byte change, including a possible Shell rewrite, conservatively preserves it and is reported in details. This preservation policy still needs the real first-launch/uninstall lifecycle test. A locked shortcut fails removal before registration values are removed, preserving retry identity. Foreign registration identity stops deletion, not takeover.

`UnicodeShellLink.cs` uses `IShellLinkW` and `IPersistFile` on one synchronous STA with explicit COM release; it never runs or resolves a target. The initial WScript.Shell approach locally rejected Japanese target paths even when an actual executable was copied there; spaces/ampersands/dollars alone worked. Explicit Unicode creation and read-back pass Japanese paths in 32-bit and 64-bit Windows PowerShell. The helper uses the system PowerShell/.NET compiler, not Visual Studio or WSL. [Unicode Shell link interface](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nn-shobjidl_core-ishelllinkw), [file persistence](https://learn.microsoft.com/en-us/windows/win32/api/objidl/nn-objidl-ipersistfile).

Test GUID keys and generated shortcuts are cleaned up; the real app-list key and Start menu are not written. CI runs this scoped native test in addition to the document-only installer fixture.

The internal registration helper also provides `VerifyUpdate` and `Update` for a same-directory transition. ## File and registration update transaction

`scripts/setup-update-transaction.ps1` is a dot-sourced primitive connected through the registered workflow and Setup entry point below. `New-TowavueUpdateTransaction` accepts the planner's three inputs plus a caller-supplied new uninstaller generated by Setup. It creates independent old/new copies of changed files and the executable in a fresh same-volume sibling directory and writes an immutable journal last, returning `TransactionDirectory` and `JournalSha256`. Unchanged non-app files are still verified/locked, but not copied: they are never mutated or automatically restored over user changes. The caller must durably retain that digest before calling `Invoke-TowavueUpdateTransaction -Mode Apply`; the digest is a corruption check, not authentication against the same user. Preparation does not change installed files.

The optional `Registration` hashtable contains exactly `RegistrySubKey` and `ShortcutPath`. Preparation uses `setup-update-registration.ps1` to verify the old key against the installed inventory ID, capture its typed previous size, and derive the new ID/size from the incoming file plan. Store the whole transition in the same immutable journal, not a separate caller-edited record. All new journals use schema 3 so earlier readers cannot resume the new two-executable guard protocol; the current reader also accepts previous internal schema-1/2 journals. Missing/foreign registration fails before creating the transaction directory. Both execution directions bind the recorded install path, old/new IDs and new size to the file plan and verify current registry state before file mutations. Omission of `Registration` retains the file-only primitive for existing fixtures; it never infers registration ownership.

Apply repeats the complete planner, verifies every staged/backup file, and acquires sharing-restricted read/write handles to all existing owned targets before mutation. It copies old security/streams into an independent work file and changes only that copy's main data stream. Windows locally refuses ordinary replacement of an open destination even with delete sharing. Therefore the transaction first moves the old name into retained storage, then moves the new work file into place without overwrite or cross-volume fallback. Validate both guard retirement destinations before either move, retire Uninstall.exe first and towavue.exe second before changing payload, even when their bytes are unchanged. Publish the app after payload and registration agree, then publish/restore the uninstaller last. Rollback follows the same ordering. A failure between the first two retirements leaves only the still-consistent old app available; mixed payload has neither installed executable entry point. No process is killed or uninstaller executed by the production helper. [Windows move semantics](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [Windows copy semantics](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-copyfilew).

Rollback may encounter an original executable still at its target: after the first new guard, a legacy app-first interruption, or an interrupted rollback that already restored the app. Validate its old hash and retire that original into the available apply-retired slot, then restore that same object. Do not require a nonexistent backup-retirement name or allocate a replacement copy. Existing occupied/unknown guard destinations are still refusal conditions before either guard move. Forty file-only/joined move boundaries assert guard presence and exact payload/registry states at publication; identical-uninstaller and legacy schema-1/2 first-app-retirement cases also recover. This prevents new launches from the installed paths, not an already running or previously self-copied legacy uninstaller; actual legacy process coordination and product lifecycle remain gates.

Rollback needs the retained directory/digest, not the original incoming tree. Before mutation it checks all current files against the recorded old/new main-stream hashes. Retired files identify the gap between the two moves; a flushed publication receipt distinguishes a later missing published file from an interrupted publication. Unknown content, corrupt recovery data/receipts and sharing failures stop and retain evidence. Restore the validated retired original by renaming it back, not by making another data-file copy: missing/locked originals or missing original parent directories stop before mutation rather than triggering an automatic copy fallback. Rollback itself is restartable at the tested move boundaries and idempotent. A used transaction cannot be applied again; prepare a new one. Restored originals return to the installation; newly rolled-back files, independent backups, receipts and any created empty directories remain recoverable; no recursive cleanup occurs.

For a bound transaction, perform the registration transition after the non-executable files have reached their target state and immediately before publishing the app, in both directions; the uninstaller follows it. A registry write failure during file changes leaves both executables retired. The same journal/digest can then Rollback both files and a known partial registry transition. Unknown registry values stop before files change. A file-unchanged operation can adjust the registry without retiring already consistent executables. Results explicitly distinguish `files_and_registration_applied`/`files_and_registration_rolled_back` from the legacy `payload_applied_registration_pending`/`payload_rolled_back` cases. A partially applied update must be rolled back before preparing a fresh attempt; this is not forward-resume support.

This is not a whole-install atomic transaction. There is a window between publication and its receipt, and the helper does not exclude hostile same-user directory renames/reparse races. It does not verify all alternate streams/security/timestamp changes or promise complete NTFS metadata fidelity. Rollback no longer allocates replacement data copies, but filesystem metadata can still require space; actual full-volume and ACL-denial recovery are not qualified. Full power-loss durability, already-running legacy uninstaller coordination, recovery UI qualification, cleanup and real Windows 10/11 product lifecycle remain gates. These helper results are not an installed-product lifecycle qualification.

`scripts/setup-registered-update.ps1` adds the internal `Invoke-TowavueRegisteredUpdate` entry point. Apply takes the preparation arguments including Registration, prepares the journal, then writes and flushes one REG_SZ `TowavuePendingUpdate` value containing its directory/digest/schema in the existing owned HKCU Registry64 key before changing installed files. Rollback needs only the selected InstallDirectory and Registration, not a caller-retained token or incoming payload. The transaction validates that the journal belongs to that exact selected install/key/shortcut before mutation. A pending record blocks another Apply; malformed, unknown-type or cross-install records are preserved. Clear only the unchanged pointer after successful Apply/Rollback; a crash after complete Apply but before clearing still permits rollback. Recovery files remain retained, not recursively cleaned.

The registered entry point and newly built Setup share a user-SID/registration-key operation lease, so different destinations competing for the same registration also conflict. A common helper derives the global object name. The first creator retains a mutex handle; later creators close their handle and refuse work. Object existence is the lease, without waiting or thread ownership, allowing NSIS section/UI cleanup on different threads. Normal completion/exit closes the handle; termination also releases it once all handles close. The durable pending pointer is independent.
